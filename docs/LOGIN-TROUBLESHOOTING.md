# رفع مشکل «نام کاربری یا رمز عبور اشتباه است» در پنل ادمین

اگر نام کاربری و رمز را درست وارد می‌کنی ولی سایت قبول نمی‌کند، به احتمال خیلی زیاد مشکل
از **رمز** نیست؛ از **جایی است که رمز در آن ذخیره شده** یا از **قفل موقت ورود**.

---

## ۱) سکرتِ گیت‌هاب ≠ سکرتِ کلودفلر (مهم‌ترین نکته)

سه جای مختلف می‌توان `ADMIN_USERNAME` / `ADMIN_PASSWORD` گذاشت و فقط **یکی** از آن‌ها روی
ورود به پنل تاثیر دارد:

| کجا گذاشته‌ای | روی چه چیزی تاثیر دارد | روی ورود به پنل؟ |
|---|---|---|
| **GitHub → Settings → Secrets and variables → Actions** | فقط ورک‌فلوهای `sync-content` و `export-content` (همگام‌سازی محتوای گیت با سایت زنده) | ❌ مستقیماً هیچ — مگر اینکه ورک‌فلوی دیپلوی آن را به کلودفلر بفرستد (پایین، بخش ۴) |
| **Cloudflare → Workers & Pages → پروژه‌ی Pages → Settings → Variables and Secrets** | محیط اجرایی Functions — همان چیزی که `functions/api/auth.ts` می‌خواند | ✅ **بله، همین منبع اصلی است** |
| فایل `.env` محلی (روی کامپیوتر خودت، gitignore شده) | فقط سرور توسعه‌ی `npm run dev` | ⚠️ فقط در حالت توسعه |

کد ورود (`functions/api/auth.ts`) مقادیر را از `env.ADMIN_USERNAME` و `env.ADMIN_PASSWORD`
و `env.AUTH_SECRET` می‌خواند؛ یعنی **محیطِ دیپلویمنتِ کلودفلر**. اگر این سه را در کلودفلر
نگذاشته باشی، سرور اصلاً سراغ مقایسه‌ی رمز نمی‌رود و `503` برمی‌گرداند.

> **نکته‌ی گیج‌کننده:** تا پیش از این، فرم ورود هر سه حالت (سکرت نبودن، قفل بودن IP، رمز
> اشتباه) را با یک پیام «نام کاربری یا رمز عبور اشتباه است» نشان می‌داد. الان پیام واقعیِ
> سرور نمایش داده می‌شود و علاوه بر آن، یک بنر تشخیصی بالای فرم ورود ظاهر می‌شود.

## ۲) تشخیص فوری: `/api/health`

در مرورگر باز کن:

```
https://omidadli01.site/api/health
```

این مسیر عمومی است و **فقط نام متغیرها و وضعیت (true/false) را نشان می‌دهد، هرگز مقدار
رمز را**. خروجی نمونه وقتی مشکل داری:

```json
{
  "ok": true,
  "ready": false,
  "message": "سرویس ورود پیکربندی نشده است — سکرت‌های Cloudflare به این دیپلویمنت نرسیده‌اند.",
  "auth": { "configured": false, "missing": ["ADMIN_USERNAME", "ADMIN_PASSWORD", "AUTH_SECRET"] },
  "bindings": { "d1": true, "r2": false },
  "login": { "locked": false, "failedAttempts": 0, "maxFailures": 8, "windowMinutes": 15 },
  "hints": [ "…راه‌حل‌های دقیق به فارسی…" ]
}
```

| چه می‌بینی | یعنی |
|---|---|
| `auth.configured: false` + لیست `missing` | سکرت‌ها در کلودفلر نیستند یا **به این دیپلویمنت نرسیده‌اند** → بخش ۳ |
| `login.locked: true` + `retryAfterMinutes` | بعد از ۸ تلاش ناموفق، ورود از IP تو ۱۵ دقیقه قفل شده → صبر کن (رمز درست هم در این مدت رد می‌شود) |
| `bindings.d1: false` | بایندینگ `DB` وصل نیست → Pages → Settings → Functions → D1 database bindings |
| همه‌چیز `true` ولی هنوز ۴۰۱ | مقدار ذخیره‌شده در کلودفلر با چیزی که تایپ می‌کنی فرق دارد → بخش ۵ |

## ۳) راه‌حل اصلی: گذاشتن سکرت‌ها **و سپس دیپلوی مجدد**

**Pages سکرت‌ها را در زمان دیپلوی به بیلد تزریق می‌کند.** یعنی سکرتی که امروز در داشبورد
اضافه می‌کنی، به نسخه‌ای که همین الان در حال سرویس‌دهی است **نمی‌رسد**؛ فقط دیپلویمنتِ
بعدی آن را می‌بیند. این شایع‌ترین دلیلِ همین مشکل است: «سکرت را گذاشتم، ولی هنوز می‌گوید
رمز اشتباه».

### الف) از داشبورد Cloudflare

1. Cloudflare → **Workers & Pages** → پروژه‌ی Pages این سایت (`my-website`)
2. **Settings → Variables and Secrets** (در پروژه‌های قدیمی‌تر: Environment variables)
3. محیط **Production** (نه فقط Preview) و برای هر سه مورد نوع **Secret (encrypted)**:

   | نام | مقدار |
   |---|---|
   | `ADMIN_USERNAME` | نام کاربری دلخواه (به بزرگی/کوچکی حروف حساس است) |
   | `ADMIN_PASSWORD` | رمز عبور |
   | `AUTH_SECRET` | یک رشته‌ی تصادفی بلند، مثلاً خروجی `openssl rand -hex 32` |

   > ⚠️ چون این پروژه `wrangler.toml` دارد، متغیرهای **متنی/معمولی (Plain text)** از طریق
   > داشبورد مدیریت نمی‌شوند و ممکن است با هر دیپلوی پاک شوند (کلادفلر همان بنر
   > «being managed through wrangler.toml» را نشان می‌دهد). پس حتماً نوع **Secret** را
   > انتخاب کن. `AUTH_SECRET` بدون آن نه ورود کار می‌کند نه توکن نشست.
4. **حتماً یک دیپلوی جدید بزن:** در تب Deployments روی آخرین دیپلوی → **Retry deployment**،
   یا یک کامیت جدید روی `main` (ورک‌فلوی `Deploy to Cloudflare Pages` خودش دیپلوی می‌کند).
5. دوباره `/api/health` را باز کن: باید `auth.configured: true` و `ready: true` باشد.

### ب) یا با Wrangler (از ترمینال)

```bash
# مقدارها را تایپ کن (پرسش مخفی) — امن‌ترین حالت
npx wrangler pages secret put ADMIN_USERNAME --project-name=my-website
npx wrangler pages secret put ADMIN_PASSWORD --project-name=my-website
npx wrangler pages secret put AUTH_SECRET    --project-name=my-website

# بعد دیپلوی کن تا سکرت‌ها به نسخه‌ی در حال سرویس برسند (ترتیب مهم است!)
npm run build
npx wrangler pages deploy dist --project-name=my-website
```

> ❌ `echo "MyPass" | npx wrangler pages secret put ADMIN_PASSWORD` — دستور `echo` یک
> **newline** به انتهای مقدار اضافه می‌کند و آن‌وقت رمزِ درست هم `401` می‌گیرد. اگر می‌خواهی
> pipe کنی از `printf '%s' 'MyPass' | …` استفاده کن.

## ۴) اگر می‌خواهی گیت‌هاب منبع حقیقت باشد (خودکار)

ورک‌فلوی `deploy.yml` الان یک قدم دارد به نام **Push admin credentials to Cloudflare**:
اگر در GitHub Secrets هم `ADMIN_USERNAME` / `ADMIN_PASSWORD` / `AUTH_SECRET` گذاشته باشی
(کنار `CLOUDFLARE_API_TOKEN` و `CLOUDFLARE_ACCOUNT_ID`)، هر دیپلوی آن‌ها را به‌صورت
**Secret رمزنگاری‌شده** در پروژه‌ی Pages می‌نویسد و **بعد** دیپلوی می‌کند — پس از این به بعد
یک مقدار در گیت‌هاب کافی است و مشکل «دیپلوی‌نشدن بعد از تغییر سکرت» هم خودکار حل می‌شود.

قدم آخرِ همان ورک‌فلو (**Verify admin login on the live site**) واقعاً با همان نام کاربری/رمز
به سایت زنده لاگین می‌کند و نتیجه را در لاگ می‌نویسد: `admin login OK` یا یک هشدار با
توضیحِ کد HTTP (رمز هیچ‌جا در لاگ چاپ نمی‌شود). برای دیدن وضعیت:
GitHub → repo → Actions → اجرای دیپلوی → این دو قدم.

> این قدم‌ها فقط وقتی فعال می‌شوند که `CLOUDFLARE_API_TOKEN` را گذاشته باشی (حالت «انتشار
> با GitHub Actions»). اگر از «Connect to Git» داخل داشبورد کلودفلر دیپلوی می‌کنی،
> ورک‌فلو دیپلوی no-op است و باید سکرت‌ها را دستی در داشبورد بگذاری (بخش ۳-الف) و
> **Retry deployment** را بزنی.

## ۵) اگر `/api/health` می‌گوید همه‌چیز آماده است ولی هنوز رد می‌شوی

آن‌وقت واقعاً مقدارِ ذخیره‌شده با چیزی که تایپ می‌کنی متفاوت است:

- **فاصله/خطای تایپی:** هنگام کپی‌پیست از یک سند یا پیام، فاصله‌ی اول/آخر یا کاراکتر نامرئی
  اضافه می‌شود. نام کاربری در کد `trim` می‌شود ولی **رمز عمداً trim نمی‌شود** (رمزی که
  فاصله دارد معتبر است)، پس فاصله‌ی انتهای رمز = ورود ناموفق.
- **بزرگی/کوچکی حروف:** هم نام کاربری و هم رمز **case-sensitive** هستند (`Admin` ≠ `admin`).
- **newline پنهان:** همان اشتباه `echo | wrangler pages secret put` (بخش ۳-ب).
- **کاراکتر فارسی/عربی یا نیم‌فاصله** در رمز: با کیبورد متفاوت تایپ شده‌اند.
- **رمز را در دو محیط گذاشته‌ای:** مقدار Preview با Production فرق دارد و تو روی دامنه‌ی
  اصلی (Production) تست می‌کنی.
- **پروژه‌ی اشتباه:** اگر بیش از یک پروژه‌ی Pages داری (یا سکرت را روی یک Worker گذاشته‌ای)،
  مطمئن شو همان پروژه‌ای است که دامنه‌ی `omidadli01.site` به آن وصل است.

ساده‌ترین راهِ اطمینان: مقدار را دوباره با `printf '%s' '…' | npx wrangler pages secret put …`
بگذار، دیپلوی کن، و بعد `/api/health`.

## ۶) قفل موقت (Rate limit)

بیش از **۸ تلاش ناموفق از یک IP در ۱۵ دقیقه** → ورود ۱۵ دقیقه قفل می‌شود (HTTP `429`).
وقتی دلیل اصلی چیز دیگری است، چند بار پشت سر هم امتحان کردن باعث می‌شود حتی بعد از رفع
مشکل هم موقتاً رد شوی. وضعیتت را در `/api/health` ببین (`login.locked`,
`login.retryAfterMinutes`)؛ یا اینترنت گوشی را عوض کن/کمی صبر کن. جدول `login_attempts` در
D1 رکوردهای قدیمی‌تر از ۲۴ ساعت را خودش پاک می‌کند.

## ۷) حالت توسعه (محلی) در برابر حالت ابری

- `npm run dev` بدون API ابری → سایت در حالت **local** است و ورود با **رمز محلی (PIN)**
  انجام می‌شود، نه با سکرت‌های کلودفلر.
- برای تست مسیر واقعی ابری به‌صورت محلی:
  ```bash
  npm run build
  npx wrangler pages dev dist --port 8788   # سکرت‌ها از فایل .dev.vars خوانده می‌شوند
  npm run dev                                # در ترمینال دوم (پروکسی /api به 8788)
  ```
- در سرور توسعه‌ی Vite، `ADMIN_USERNAME`/`ADMIN_PASSWORD`/`AUTH_SECRET` از فایل `.env`
  خوانده می‌شوند (این فایل در `.gitignore` است). `http://localhost:3000/api/health` همان
  تشخیص را برای محیط توسعه نشان می‌دهد.
